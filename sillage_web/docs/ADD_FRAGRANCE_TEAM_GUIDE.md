# Add Fragrance team implementation guide

The website form, input validation, admin/customer connection selection, success display, and friendly error handling are ready. The database INSERT function is intentionally unfinished because the assignment reserves required SQL, parameterization, and database save/error logic for your team.

The two functions you supplied, `stock_location` and `top_seller`, are included unchanged in `student_code/reports.py`. No new implementation is needed for those functions.

## 1. Write the database function

Complete `student_code/fragrances.py`. Keep this interface so the existing website can call it:

```python
def add_fragrance(connection, fragrance_name, strength, size, price, brand_id,
                  perfumer_id=None, notes=None):
```

The signature above is application boilerplate, not the database implementation. The scaffold currently raises NotImplementedError. Your team must write the function body, including its SQL and parameter binding.

| Python input | SQL column in Fragrance | Contract supplied by the website |
| --- | --- | --- |
| `fragrance_name` | `Fragrance_Name` | Required string, maximum 100 characters. |
| `strength` | `Strength` | Required string, maximum 45 characters. |
| `size` | `Size` | Positive integer, in millilitres. |
| `price` | `Price` | Python Decimal; nonnegative, up to 99999999.99, at most two decimal places. |
| `brand_id` | `Brand_ID` | Positive integer for an existing Brand. |
| `perfumer_id` | `Perfumer_ID` | Positive integer for an existing Perfumer.Person_ID, or None. A Person row alone does not establish that the person is a Perfumer. |
| `notes` | `Notes` | Descriptive text up to 255 characters, or None. |

Your SQL task is to insert **one row into Fragrance** using these fields and parameterize every user-provided value. Fragrance_ID is generated by MySQL. The form's descriptive Notes field is not the separate Fragrance_Note relationship, and this action does not create inventory, brands, or perfumers. Those are separate database actions.

Your Python implementation must use the supplied connection, execute your parameterized statement, obtain the new Fragrance_ID, and return that positive integer only after the change has been successfully saved. Your team owns the commit/rollback and error handling. Connector/Python does not enable autocommit by default; returning an ID without saving is not enough.

On a database failure, preserve and propagate the original MySQL exception after your cleanup/error handling. In particular, do not turn a permission error into a generic string or return None: the web layer needs the exception's errno to show the correct message. Close your cursor; the service closes the supplied connection. Do not open another connection, switch users, or catch a failure and retry as admin inside this function.

After implementing and testing it, set `ADD_FRAGRANCE_READY = True` in that same module and restart the web server. Until then, submitting the form displays **“Adding fragrances is not available yet.”** This is not presented as a MySQL refusal.

## 3. Configure the connections

From the extracted `sillage_web` folder:

```bash
python -m pip install -r requirements.txt
python app.py --staff --fragrance-accounts
```

The prompts collect the base application's MySQL password, the customer database password, the admin database password, and a separate team-desk password for the website. All database accounts must be non-root.

| Configuration | Default / purpose |
| --- | --- |
| `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_DATABASE` | localhost, 3306, scent_db; common to all three profiles. |
| `MYSQL_USER`, `MYSQL_PASSWORD` | Base application account, default scent_app; used by the existing features and the two new reports. |
| `MYSQL_CUSTOMER_USER`, `MYSQL_CUSTOMER_PASSWORD` | Add Fragrance customer profile; username defaults to customer when the optional profiles are enabled. |
| `MYSQL_ADMIN_USER`, `MYSQL_ADMIN_PASSWORD` | Add Fragrance admin profile; username defaults to admin when the optional profiles are enabled. |
| `SILLAGE_STAFF_PASSWORD` | Optional alternative to the website team-desk password prompt. |

Passwords may be supplied through the environment or entered at startup. The role-specific passwords never fall back to the base account password. Both role profiles must be configured together and must have distinct usernames. Setting any MYSQL_CUSTOMER_* or MYSQL_ADMIN_* variable enables their configuration even without the flag.

The new connection profiles apply **only to Add Fragrance**. Existing searches, registration, purchases, revenue, stock location, and top sellers continue using the base configured account. Signing in to the team desk changes the server session; it does not expose a database username/password to the browser.

Real customer email/password login is not implemented yet. For this classroom demonstration, all visitors without a staff session use customer-level database access for Add Fragrance. That is a database-access category, not verification of a particular Customer row.

## 4. Demonstrate the actual database refusal

1. Verify your completed function and the effective grants using test data. Choose a valid existing Brand ID and, if supplied, a valid Perfumer ID. Use a new fragrance/strength/size combination so duplicate-data errors do not mask the test.
2. Start live mode with the three non-root account profiles. Preview mode never writes or produces a fake MySQL refusal.
3. Without signing in to the team desk, open **Add Fragrance** and submit valid test values. Python selects the customer connection and calls the student function. There is no role-based pre-rejection for this endpoint.
4. With the expected grants, MySQL rejects the INSERT. Error 1142 or 1143 on this customer request produces exactly:

   > It looks like you can't add a fragrance! Come into one of our stores, or email us, and we will try to get the fragrance for you!

5. Verify that no row was added. A disabled button, a generic unavailable message, or an HTTP 403 from an application-only check does not prove MySQL refusal.
6. Sign in to the team desk using the separate website password. Open Add Fragrance again and submit the valid values. The server selects the admin connection. After a successful student-owned insert/save, the website shows the new ID and refreshes the catalogue.
7. Sign out and repeat with a different valid fragrance combination to confirm the customer connection is selected again. Client-supplied role/user fields do not affect connection selection.

If your customer account actually has INSERT permission, MySQL may accept and save its request. The website does not fabricate a rejection or undo a successful student function to make the demo look correct. Check and correct the team-owned grants before presenting.

Other conditions have different messages: duplicate variants, invalid foreign keys, connection failures, absent role configuration, and the unimplemented function are not called permission refusals. The requested message does not send an email or save a customer request.
